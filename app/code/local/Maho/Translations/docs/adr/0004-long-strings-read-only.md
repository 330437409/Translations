# ADR-0004：超过 255 字符的文案第一期只读

## 状态

已接受。已被 [ADR-0008](0008-long-translations.md) 取代。

## 背景

`core_translate` 的 `string` 和 `translate` 列都是 `VARCHAR(255)`。Maho 的界面文案大多较短，但 `app/locale/en_US` 里仍有约 27 条源文案超过 255 字符。翻译后的长度还可能超过原文。

要支持超长文案，需要改核心表结构、增加模块表并在运行时合并，或者重写翻译器。三种方案都会扩大第一期范围。

## 决策

第一期以 `core_translate` 为唯一写入目标。超过 255 字符的源文案仍然扫描、索引和展示，但标记为 `is_supported = 0`，编辑页只读，CSV 导入拒绝，CSV 导出仍可带出。第二期再决定超长文案的存储和运行时方案。

## 理由

- 不修改 Maho 核心表，避免升级和跨数据库迁移风险。
- 不影响绝大多数界面文案的管理。
- 超长文案数量少，可以先用 CSV 或语言包维护。
- 把复杂度留给第二期，先把主流程做稳。

## 后果

- 后台会明确告诉用户哪些文案暂不支持编辑。
- CSV 导入遇到超长文案会整批失败，需要在文件里先移除或标记。
- 如果用户大量依赖超长文案，第一期体验会受限。
- 第二期需要单独设计长文案表、运行时合并和缓存策略。

## 备选方案

- **把 `core_translate` 列改成 TEXT**：需要改核心表、处理索引长度和升级，风险高，不采用。
- **新增模块长文案表并重写翻译器**：能完整支持，但回到 ADR-0001 反对的重写路线，不采用。
- **长文案写模块 CSV**：只能按 locale 生效，不能按 store 覆盖，复杂度也不低，暂不采用。
