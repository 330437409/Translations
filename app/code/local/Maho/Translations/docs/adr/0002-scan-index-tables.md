# ADR-0002：使用扫描索引表和声明式 schema

## 状态

已接受。

## 背景

后台网格需要按 locale、store、状态、模块、area 和文本筛选，还要显示文案在代码里的位置，以及缺失和未使用状态。每次请求都解析全部语言包和源码会很慢，也无法稳定分页和排序。

Maho 从 26.7 起支持 `sql/schema.php` 声明式建表，由 DBAL 负责 MySQL、MariaDB、PostgreSQL 和 SQLite 的 DDL 差异。

## 决策

新增三张索引表：

- `translation_source`：源文案和汇总状态。
- `translation_location`：源文案在文件中的位置。
- `translation_pack`：语言包翻译的规范快照。

另加一张 `translation_scan` 记录扫描状态和统计。表结构全部写在 `sql/schema.php`，不写 MySQL 专用的 install 脚本。

## 理由

- 网格可以直接用数据库分页、排序和筛选，数据量大时仍然稳定。
- 缺失和未使用分析可以在扫描时一次算好，不用每次请求重新解析。
- 位置表支持“这条文案在哪里用”的排查。
- 声明式 schema 自动适配四种数据库，符合 Maho 新模块规范。
- 索引表可以随时重建，不承载运行时翻译，损坏后重新扫描即可恢复。

## 后果

- 扫描需要写入约 1 万条源文案和更多位置记录，必须使用批量插入和事务。
- 语言包更新后需要重新扫描，索引不会自动跟随 Composer 更新。
- 索引表会占用额外空间，但规模远小于订单和商品数据。
- 扫描期间 SQLite 会短暂锁库，需要控制扫描时长。

## 备选方案

- **每次请求解析 CSV 和源码**：实现简单，但性能不可接受，也无法稳定分页，不采用。
- **只索引 CSV，不索引源码位置**：网格够用，但无法回答“在哪里用”和“是否未使用”，不采用。
- **把索引放在缓存里**：不占数据库，但多服务器、缓存淘汰和网格筛选都更复杂，不采用。
